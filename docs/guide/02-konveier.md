воно працює, обробити дані призначеним інструментом і прийняти потік

Подивіться у свій маніфест (крок 0.6) на два поля:

| Поле | Можливі значення | Що потрібно встановити |
|---|---|---|

можна пропустити.

## 2.2. Docker (для InfluxDB, TimescaleDB і Grafana)

InfluxDB і TimescaleDB — це серверні бази даних. Щоб не встановлювати їх
вручну, ми запускаємо їх у Docker: готові «контейнери», які піднімаються
однією командою. Docker Desktop безкоштовний для навчання.

### Windows 10/11

1. **Віртуалізація.** Відкрийте Диспетчер завдань → **Продуктивність** →
   **ЦП**. Внизу має бути «Віртуалізація: Увімкнено». Якщо «Вимкнено» — її
   вмикають у BIOS/UEFI; інструкція Microsoft:
   <https://support.microsoft.com/en-us/windows/enable-virtualization-on-windows-c5578302-6e43-4b4b-a449-8ced115f58e1>.
2. **WSL 2.** Відкрийте PowerShell **від імені адміністратора** (правою
   кнопкою на PowerShell → «Запуск від імені адміністратора») і виконайте:

   ```powershell
   wsl --install
   ```

   Перезавантажте комп'ютер.
3. **Docker Desktop.** Завантажте інсталятор з
   <https://docs.docker.com/desktop/setup/install/windows-install/>. Під час
   встановлення залиште позначку **Use WSL 2 instead of Hyper-V**.
4. Запустіть Docker Desktop і дочекайтеся внизу ліворуч статусу «Engine
   running».

**Увага.** Docker Desktop працює на Windows 10/11 через WSL 2, зокрема й на
Windows Home; документація Docker вимагає 8 ГБ оперативної пам'яті. Якщо у
вас він не запускається — одразу повідомте керівника, не витрачайте на це
вечір.

### macOS

Завантажте `Docker.dmg` з
<https://docs.docker.com/desktop/setup/install/mac-install/> (окремо для
Apple Silicon і Intel), перетягніть у «Програми», запустіть і прийміть
угоду. Входити в акаунт не обов'язково.

### Linux (Ubuntu)

Найлегший варіант — Docker Engine:
<https://docs.docker.com/engine/install/ubuntu/>. Після встановлення
виконайте кроки з <https://docs.docker.com/engine/install/linux-postinstall/>,
щоб запускати Docker без `sudo`, і вийдіть із системи та зайдіть знову.

### Запуск баз даних

Docker Desktop має бути запущений. З папки проєкту:

```bash
docker compose -f pipeline/docker-compose.yml up -d
```

Перший запуск завантажує образи (близько 2 ГБ) — це займе кілька хвилин.
Перевірка:

```bash
docker compose -f pipeline/docker-compose.yml ps
```

```
NAME                  IMAGE                               COMMAND                  SERVICE       CREATED          STATUS                    PORTS
kursova-influxdb      influxdb:2.7                        "/entrypoint.sh infl…"   influxdb      32 minutes ago   Up 32 minutes (healthy)   127.0.0.1:8086->8086/tcp
kursova-timescaledb   timescale/timescaledb:latest-pg16   "docker-entrypoint.s…"   timescaledb   32 minutes ago   Up 21 seconds (healthy)   127.0.0.1:5432->5432/tcp
```

**Перевірка.** У колонці STATUS — `(healthy)`. Для InfluxDB можна ще
відкрити в браузері <http://localhost:8086> (логін `student`, пароль
`kursova2025`).

Зупинити, коли не працюєте (дані зберігаються):

```bash
docker compose -f pipeline/docker-compose.yml stop
```

**Увага.** Ніколи не додавайте `-v` до `docker compose down` — це видалить
усі завантажені дані.

## 2.3. Завантаження і вимірювання

Усі обов'язкові вимірювання стадії (п. 4.2 вказівок) робить один скрипт
`pipeline/measure.py`. Він завантажує файл у ваше сховище і вимірює:
розмір у CSV і Parquet, швидкість завантаження, розмір сховища, час повного
сканування, час вибірки за пристроєм, пам'ять і межу, за якою дані перестануть
уміщатися в пам'ять.

### Спочатку — на навчальному наборі

Вкажіть **своє** сховище в `--storage` (як у маніфесті, в лапках):

```bash
python pipeline/measure.py --storage "DuckDB + Parquet" --data tuning.parquet --scale-test --out measure_tuning.csv
```

Справжній вивід (комп'ютер Apple M1, 16 ГБ):

```
### Вимірювання стадії 2: DuckDB + Parquet, tuning.parquet

Тестова машина: Apple M1 (8 ядер / 8 потоків), RAM 16,0 ГБ, macOS 26.7.1 (arm64), Python 3.12.14.

| Показник | Значення |
|---|---|
| Записів у наборі | 1 157 147 |
| Обсяг у CSV | 44,7 МБ |
| Обсяг у Parquet | 5,3 МБ |
| Коефіцієнт стиснення (CSV / Parquet) | 8,5 |
| Пропускна здатність завантаження | 5 851 988 записів/с (1 157 147 за 0,20 с) |
| Розмір сховища на диску | 8,4 МБ (файл бази duckdb) |
| Повне сканування (кількість і середнє за кожним показником) | 0,004 с |
| Вибірка за одним пристроєм (co2-01-wor, записів: 9 692) | 0,003 с |
| Пікова пам'ять процесу Python (завантаження і запити) | 293,4 МБ (до завантаження 186,1 МБ) |
| Весь файл у pandas: пам'ять на один запис | 14,0 Б у DataFrame, до 66,8 Б під час читання |
| Межа: вміститься у 16,0 ГБ RAM | ≈ 257 млн записів ≈ 222× цей набір |
```

Таблиця не лише друкується, а й зберігається у файл `measure_tuning.md`
(і `measure_tuning.csv`, бо ми вказали `--out`) — його можна вставити у звіт.
Без `--out` файл називається за сховищем (`measure_duckdb.md`), і наступний
запуск з тим самим сховищем його перезапише.

### Потім — на своєму варіанті

```bash
python pipeline/measure.py --data variant_NNN.parquet --scale-test
```

Без `--storage` скрипт сам бере сховище з вашого маніфесту. На наборі з 7 млн
записів вимірювання триває від 15 секунд (DuckDB) до хвилини (InfluxDB).

**InfluxDB.** Одразу після завантаження InfluxDB тримає дані в робочому
журналі, і розмір на диску завищений. Приблизно через 10 хвилин
переміряйте лише розмір:

```bash
python pipeline/measure.py --storage InfluxDB --size-only
```

**Порада.** Закрийте важкі програми (браузер з десятками вкладок, ігри) і
повторіть вимірювання двічі: числа можуть відрізнятися на 30–50 %.

### Що означає кожен рядок

| Рядок | Як розуміти |
|---|---|
| Обсяг у CSV / Parquet | Ті самі дані у двох форматах. CSV — текст, Parquet — стовпцевий двійковий формат зі стисненням |
| Коефіцієнт стиснення | У скільки разів Parquet менший. Поясніть у звіті, звідки така різниця |
| Пропускна здатність | Скільки записів за секунду сховище приймає |
| Розмір на диску | Скільки місця займають дані всередині сховища (разом з індексами) |
| Повне сканування | Час запиту, який мусить прочитати **всі** записи |
| Вибірка за пристроєм | Час, щоб дістати дані одного пристрою, — те, що постійно роблять детектори |
| Пікова пам'ять | Найбільше пам'яті, яку займав скрипт |
| Межа пам'яті | Скільки записів поміститься в пам'ять вашого комп'ютера, якщо читати файл цілком |

### Межа пам'яті

Вказівки вимагають оцінити, за якого обсягу дані вже не вмістяться в
оперативну пам'ять. Ваш варіант ще вміщується (кілька сотень мегабайтів), але
реальні системи накопичують у сотні разів більше. Параметр `--scale-test`
читає файл, складений з 1, 2 і 4 копій ваших даних, і показує, що пам'ять
росте **лінійно**:

```
| Копій | Записів | Файл Parquet | DataFrame у пам'яті | Пік під час читання | Пік на запис |
|---|---|---|---|---|---|
| 1× | 1 157 147 | 5,3 МБ | 16,2 МБ | 77,3 МБ | 66,8 Б |
| 2× | 2 314 294 | 10,8 МБ | 32,4 МБ | 138,7 МБ | 59,9 Б |
| 4× | 4 628 588 | 21,6 МБ | 64,8 МБ | 265,3 МБ | 57,3 Б |

Пам'ять росте лінійно: ≈ 14,0 МБ + 54,2 Б на кожен запис. За цією прямою 16,0 ГБ RAM закінчаться на ≈ 316 млн записів.
```

Межа тут (≈ 316 млн) більша, ніж у першій таблиці (≈ 257 млн): там пам'ять
на запис рахується з одного читання, де стала частина (≈ 14 МБ) припадає на
порівняно мало записів; пряма за трьома розмірами відокремлює цю сталу
частину. У звіт наводьте межу за прямою і поясніть різницю.

**У звіт (підрозділ 2.3).** Ця таблиця, пряма «стільки-то байтів на запис»,
межа для вашого комп'ютера і як ви її обходите: читання порціями (2.4),
стовпцеве зберігання, фільтрація на рівні сховища (запит повертає лише
потрібний пристрій).

### Для порівняння: усі чотири сховища

Ось що показали ті самі вимірювання на файлі з 6,9 млн записів (розмір
типового варіанта) на тестовому комп'ютері. Ваші числа будуть іншими, але
співвідношення — схожими.

| Сховище | Завантаження, записів/с | На диску | Повне сканування | Один пристрій |
|---|---|---|---|---|
| DuckDB | 9,2 млн | 51 МБ | 0,014 с | 0,015 с |
| SQLite | 0,46 млн | 542 МБ | 4,27 с | 0,123 с |
| InfluxDB | 0,15 млн | 38 МБ | 0,62 с | 0,215 с |
| TimescaleDB | 0,21 млн | 1006 МБ | 0,62 с | 0,093 с |

Подумайте для звіту, чому стовпцевий DuckDB і на порядки швидший, і менший
за рядковий SQLite, і чому TimescaleDB займає найбільше місця.

## 2.4. Обробка призначеним інструментом

Для кожного з чотирьох інструментів є приклад у папці `processing/`. Усі
чотири приклади рахують однакові дві таблиці, тож результат можна порівнювати:

- `results/daily_stats.parquet` — для кожного пристрою, показника і доби:
  кількість, середнє, мінімум, максимум;
- `results/hourly_messages.parquet` — скільки повідомлень надіслав кожен
  пристрій за кожну годину. Ця таблиця дуже знадобиться на стадії 5.

## 2.5. Потоковий вхід

Другий вхід конвеєра — повідомлення вашого вузла з Wokwi у реальному часі.
Запустіть симуляцію (стадія 1), а в терміналі:

```bash
python pipeline/consumer.py --variant 47 --device esp32-047 --minutes 10
```

(номер варіанта і `DEVICE_ID` — як у вашій прошивці). Справжній вивід
хвилинного запуску для демонстраційного вузла
(`--variant 999 --device esp32-999 --minutes 1`):

```
підключено до broker.hivemq.com:1883
підписка на kursova/999/esp32-999/#
  [status] esp32-999: ОФЛАЙН (збережений брокером статус)
  [status] esp32-999: онлайн

завершено 2026-10-08T17:57:13+00:00
  прийнято записів : 33
  нерозібраних     : 0
  подій status     : 2
  файл             : stream.parquet
```

Повідомлення записуються у `stream.parquet` у тому самому форматі, що й ваш
варіант (плюс номер `seq` і час отримання `received_at`). Перший рядок
`ОФЛАЙН` — це збережене брокером повідомлення з попереднього запуску вузла
(так працює прапорець `retain`); другий — свіжий статус після старту
симуляції.

**Увага.** Не завантажуйте `stream.parquet` у те саме сховище, що й ваш
варіант: `load_parquet` щоразу **замінює** дані. Для потоку відкрийте окрему
базу, наприклад `open_storage("duckdb", database="stream.duckdb")`.

**У звіт.** Скільки повідомлень прийнято, чи були пропуски номерів `seq`
(втрачені повідомлення) і яка затримка між `ts` і `received_at`. Усе це
порахує одна команда:

```bash
python -c "import pandas as pd; d = pd.read_parquet('stream.parquet').sort_values('seq'); lag = d['received_at'] - d['ts']; print('повідомлень:', len(d)); print('пропущено номерів seq:', int(d['seq'].max() - d['seq'].min() + 1 - d['seq'].nunique())); print('затримка, с: медіана', lag.median(), ', найбільша', lag.max())"
```

Якщо у файлі кілька пристроїв або ви перезапускали вузол (тоді `seq`
починається з нуля знову), рахуйте пропуски для кожного запуску окремо.
