# Методичні вказівки до виконання курсового проєкту

## з дисципліни «Основи інтернету речей та аналітика великих даних»

---

## 1. Загальні положення

Курсовий проєкт є підсумковою самостійною роботою студента з дисципліни
«Основи інтернету речей та аналітика великих даних». Метою проєкту є
практичне опанування повного життєвого циклу даних інтернету речей: від
формування телеметрії на кінцевому пристрої, через її передавання
телекомунікаційним протоколом та зберігання у придатному для аналітики
форматі, до виявлення аномальної поведінки пристроїв у масиві обсягом
кілька мільйонів записів.

Основними завданнями виконання курсового проєкту є:

- опанування архітектури систем інтернету речей та протоколів передавання
  телеметрії (MQTT), включно з питаннями захищеності каналу;
- набуття навичок проєктування конвеєра обробки даних, здатного
  працювати з обсягами, що перевищують оперативну пам'ять робочої станції;
- опанування методів виявлення аномалій у часових рядах та оцінювання
  їхньої якості за метриками повноти і точності;
- розвиток здатності самостійно інтерпретувати результати аналізу та
  обґрунтовувати висновки за відсутності наперед відомої відповіді.

**Ключова особливість проєкту.** Кожен студент отримує власний,
неповторний набір даних. Інциденти, які необхідно виявити, у кожному
варіанті різні за складом, часом виникнення та переліком уражених
пристроїв. Еталонні відповіді зберігаються виключно у керівника. Через це
результат роботи є індивідуальним і не може бути запозичений.

---

## 2. Тема курсового проєкту

> **Проєктування системи збору та аналітики великих даних
> IoT-інфраструктури з виявленням аномалій та ознак компрометації
> пристроїв**
>
> *(варіант № N)*

Об'єкт дослідження — телеметрія розподіленої мережі давачів розумної
будівлі. Предмет дослідження — методи виявлення відмов обладнання та ознак
несанкціонованої активності за даними телеметрії.

---

## 3. Вхідні дані: індивідуальний варіант

Кожен студент отримує номер варіанта та три складники вхідних даних.

### 3.1 Власний набір даних

Файл `variant_NNN.parquet` — телеметрія змодельованої будівлі за 60 діб.

| Характеристика | Значення |
|---|---|
| Обсяг | 4,1 – 7,3 млн записів |
| Пристроїв | 45 – 71 |
| Зон | 5 – 8 |
| Період | 60 діб, з 1 вересня 2025 р. |
| Розмір файлу | 19 – 33 МБ (Parquet, zstd) |

Структура таблиці — «довгий» формат:

| Стовпець | Тип | Опис |
|---|---|---|
| `ts` | int64 | мітка часу, секунди епохи UTC |
| `device_id` | string | ідентифікатор пристрою |
| `metric` | string | назва показника |
| `value` | float32 | значення показника |

Атрибути пристроїв (зона, шлюз, тип, інтервал опитування) у таблиці
**відсутні** — їх необхідно приєднати з файлу-маніфесту. Це відповідає
усталеній практиці нормалізації даних телеметрії.

### 3.2 Маніфест

Файл `variant_NNN.json` містить інвентаризаційний опис: перелік
зареєстрованих пристроїв, їхні типи, зони, шлюзи, номінальні інтервали
опитування, одиниці вимірювання показників, а також **призначений стек
технологій** (п. 3.3).

> **Увага.** Маніфест описує пристрої, які *мають* бути у мережі. Він не
> описує того, що в ній відбувається насправді.

### 3.3 Призначений стек технологій

Для кожного варіанта визначено обов'язковий набір інструментів:

| Складник | Можливі значення |
|---|---|
| Сховище | DuckDB + Parquet, SQLite + Parquet, InfluxDB, TimescaleDB |
| Обробка | pandas (порційна), Polars, DuckDB SQL, Dask |
| Детектор № 2 | Isolation Forest, Local Outlier Factor, STL + ESD, EWMA control chart, Matrix Profile |
| Візуалізація | Grafana, Streamlit, Plotly Dash |

Використання призначеного стека є обов'язковим. Застосування інших
інструментів додатково до призначених не обмежується.

## 4. Порядок виконання

Робота виконується у шість стадій. Орієнтовна трудомісткість — 55–60 годин:
близько 46 годин на стадії, решта — на оформлення пояснювальної записки та
підготовку до захисту.

### 4.1 Стадія 1. Пристрій інтернету речей (≈ 5 год)

На базі симулятора **Wokwi** (виконується у браузері; апаратне забезпечення
не потрібне, безкоштовного тарифу достатньо) розробити вузол на
мікроконтролері ESP32, який публікує показання давачів за протоколом MQTT.

Обов'язкові складники:

1. щонайменше два давачі, показання яких публікуються окремими
   повідомленнями;
2. відповідність схемі повідомлення, наведеній у Додатку А;
3. реєстрація **Last Will and Testament** — повідомлення, яке брокер
   публікує самостійно у разі аварійного від'єднання вузла;
4. кодування того самого повідомлення у форматі CBOR із вимірюванням
   скорочення обсягу порівняно з JSON (результат навести у звіті як
   число); публікація у топіки залишається у форматі JSON згідно з
   Додатком А.

**Дослідження захищеності каналу.** Виконати послідовно та задокументувати:

1. підписатися на власний топік зі стороннього клієнта та отримати
   телеметрію у відкритому вигляді;
2. повторити те саме з іншого комп'ютера;
3. розгорнути на власному комп'ютері брокер Mosquitto з TLS та
   автентифікацією, підключити до нього вузол, емульований мовою Python
   (з тими самими вимогами до протоколу), повторити спробу перехоплення й
   пояснити результат.

Крок 3 виконується з Python-вузлом, оскільки на безкоштовному тарифі
симульований у Wokwi вузол не має доступу до локальної мережі студента.

У звіті навести знімки перехопленого трафіку до і після впровадження TLS
та висновок щодо ризику витоку телеметрії у відкритих розгортаннях.
Wokwi дозволяє зберегти трафік симульованого вузла у файл PCAP для
аналізу у Wireshark.

> За неможливості скористатися Wokwi допускається програмна емуляція
> всього вузла мовою Python із тими самими вимогами до протоколу; оцінка
> за складник «Вузол IoT, MQTT, захищеність каналу» знижується на 3 бали.
> Використання Python-вузла на кроці 3 дослідження захищеності каналу
> оцінки не знижує.

### 4.2 Стадія 2. Конвеєр обробки даних (≈ 14 год)

Реалізувати конвеєр із двома входами: потоковим (MQTT від власного вузла)
та пакетним (завантаження файла варіанта у призначене сховище).

Обов'язкові вимірювання, які наводяться у звіті:

- обсяг даних у форматах CSV та Parquet, коефіцієнт стиснення;
- час виконання повного сканування та вибірки за одним пристроєм;
- пікове споживання оперативної пам'яті;
- пропускна здатність завантаження, записів за секунду.

Індивідуальний набір даних ще вміщується в оперативну пам'ять сучасної
робочої станції, проте реальні системи інтернету речей накопичують на
порядки більші обсяги. Тому під час виконання стадії студент має оцінити —
експериментально (кратним збільшенням обсягу даних) або розрахунково (за
виміряним споживанням пам'яті на один запис), — за якого обсягу
безпосереднє завантаження всього масиву в пам'ять стає неможливим, і
обґрунтувати обраний спосіб подолання цієї межі (порційне читання,
стовпцеве зберігання, перенесення фільтрації на рівень сховища).

### 4.3 Стадія 3. Побудова детекторів (≈ 6 год)

Надається **навчальний набір** (`tuning.parquet`) — невеликий масив тієї
самої структури, для якого перелік інцидентів **відомий** і додається у
відкритому вигляді у файлі `tuning_truth.json`.

| Характеристика | Значення |
|---|---|
| Обсяг | 1,16 млн записів, 5,3 МБ |
| Пристроїв | 51 |
| Період | 14 діб |
| Інцидентів | 12 — по одному кожного класу з розділу 7 |

Навчальний набір однаковий для всіх студентів. Його призначення —
побачити характерний вигляд кожного класу інцидентів за умов, коли
відповідь відома, і налаштувати на цьому детектори.

Реалізувати два детектори:

1. **базовий статистичний** — на вибір студента (рухоме вікно, z-оцінка,
   контрольна карта тощо);
2. **призначений** — відповідно до п. 3.3.

Налаштувати обидва на навчальному наборі, досягти прийнятних значень
точності та повноти, навести їх у звіті.

### 4.4 Стадія 4. Перевірка на реальних даних (≈ 5 год)

Застосувати налаштовані детектори до **реального** набору даних давачів —
**Intel Berkeley Research Lab**, 54 вузли Mica2Dot, 28 лютого – 5 квітня
2004 р.

| Характеристика | Значення |
|---|---|
| Джерело | `https://db.csail.mit.edu/labdata/labdata.html` |
| Файл показань | `data.txt.gz` — 34 МБ стиснутий, 150 МБ розпакований |
| Координати вузлів | `mote_locs.txt` |
| Обсяг | ≈ 2,3 млн показань |
| Періодичність | 31 с |
| Показники | temperature, humidity, light, voltage |

Структура рядка (значення розділені пробілами):

```
date:yyyy-mm-dd  time:hh:mm:ss.xxx  epoch:int  moteid:int
temperature:real  humidity:real  light:real  voltage:real
```

Умови використання дозволяють вільне відтворення даних за умови
посилання на джерело; посилання обов'язкове у списку використаних джерел.

Реальні дані містять пропуски епох, відсутні або обірвані записи окремих
вузлів, а також повільну деградацію показань через розряд елементів
живлення — за документацією джерела, гарантії щодо якості даних не
надаються. Завданням стадії є встановити, які спрацювання детекторів є
хибними, та доопрацювати попередню обробку.

> Еталонного переліку аномалій для цього набору не існує. Висновки щодо
> того, які спрацювання є хибними, студент обґрунтовує самостійно.

У звіті навести: перелік виявлених проблем реальних даних, вжиті заходи,
зміну кількості хибних спрацювань до і після доопрацювання.

### 4.5 Стадія 5. Пошук інцидентів у власному варіанті (≈ 10 год)

Застосувати доопрацьовані детектори до власного набору даних.

У кожному варіанті приховано **від 5 до 8 інцидентів** класів, наведених у
розділі 7. Кількість, класи, час виникнення та уражені пристрої у кожному
варіанті різні й студенту не повідомляються.

Для кожного виявленого інциденту визначити: уражені пристрої, час початку
та завершення, клас, ступінь упевненості. Результат оформити згідно з
п. 6.2.

Частина інцидентів не виявляється аналізом окремого показника й потребує
зіставлення кількох пристроїв між собою.

### 4.6 Стадія 6. Візуалізація (≈ 6 год)

Засобами призначеного інструменту побудувати дашборд, що містить:
огляд стану мережі загалом, деталізацію за окремим пристроєм та часову
шкалу виявлених аномалій. Дашборд має залишатися придатним до
використання особою, яка не є його автором.

Обсяг — **25–30 сторінок** без урахування додатків.

```

Картка результатів            (п. 6.1, одразу після титульного аркуша)
Зміст

РОЗДІЛ 1. Теоретична частина                                 7–8 с.
  1.1 Архітектура систем інтернету речей
  1.2 Протоколи передавання телеметрії та їх захищеність
  1.3 Характеристики великих даних, архітектури обробки
  1.4 Методи виявлення аномалій у часових рядах

  2.2 Реалізація вузла та протоколу передавання

  2.4 Реалізація детекторів
```

наводяться з зазначенням умов вимірювання (конфігурація обладнання, обсяг
даних).

## 6. Результати, що здаються

До захисту подаються:

1. пояснювальна записка;
2. репозиторій з усім програмним кодом;
3. файл `findings.json`;
4. дашборд (працездатний) та знімки екрана у додатках;
5. презентація на 7 хвилин.

### 6.1 Картка результатів

Розміщується **одразу після титульного аркуша** пояснювальної записки
у вигляді таблиці. Значення обчислюються студентом самостійно з власного
набору даних.

| Поле | Опис |
|---|---|
| Варіант | номер варіанта |
| Кількість записів | загальна кількість рядків у наборі |
| Пристроїв у маніфесті | за файлом `variant_NNN.json` |
| Пристроїв у даних | унікальних `device_id` у телеметрії |
| SHA-256 переліку пристроїв | хеш відсортованого переліку з маніфесту |
| Записів за показниками | кількість рядків для кожного `metric` |
| Призначений стек | згідно з маніфестом |
| Точність / повнота | за кожним детектором, на навчальному наборі |
| Пропускна здатність | записів за секунду під час завантаження |

> Розбіжність між кількістю пристроїв у маніфесті та в даних не є
> помилкою генерації.

### 6.2 Формат `findings.json`

Приклад для навчального набору (варіант 0):

```json
{
  "variant": 0,
  "fingerprint": {
    "rows": 1157147,
    "devices_observed": 52,
    "device_list_sha256": "1a33058d…"
  },
  "findings": [
    {
      "devices": ["power-04-wor"],
      "class": "energy_anomaly",
      "start": "2025-09-11T19:00:00Z",
      "end":   "2025-09-12T01:40:00Z",
      "confidence": 0.86,
      "evidence": "Споживання ≈1,4 кВт протягом 6,7 год — удвічі більше, ніж у ті самі години інших діб; давачі руху зони workshop активності не фіксують"
    }
  ]
}
```

Час подається у форматі ISO-8601 (UTC) або як секунди епохи. Поле
`devices` може містити кілька пристроїв, якщо інцидент охопив групу.

**Правила зарахування.**

- Оцінюються не більше 15 знахідок — із найвищим значенням `confidence`
  (за рівних значень — ті, що розташовані у файлі раніше); решта не
  враховується. Відсутнє значення `confidence` вважається нулем.
- Знахідка зараховується, якщо щонайменше п'ята частина вказаних у ній
  пристроїв належить до еталонного інциденту, а часові інтервали
  перекриваються не менше ніж на 25 % (за мірою Жаккара).
- Кожен еталонний інцидент зараховується не більше одного разу: повторні
  знахідки того самого інциденту вважаються хибними спрацюваннями.
- Правильно виявлений інцидент із помилково визначеним класом
  зараховується з коефіцієнтом 0,7. Назва класу має точно збігатися з
  наведеною у розділі 7.
- Кожне хибне спрацювання зменшує оцінку за складник на 5 %, сумарно не
  більше ніж на 30 %.

## 7. Класи інцидентів

Перелік класів є вичерпним: усі приховані інциденти належать до наведених
нижче. Назва класу вказується у полі `class` латиницею.

### 7.1 Прості

| Клас | Опис |
|---|---|
| `stuck_at` | давач повертає незмінне значення |
| `outage` | пристрій припиняє передавання |
| `spike_storm` | серії фізично неможливих показань |
| `rogue_device` | у даних присутній пристрій, відсутній у маніфесті |

### 7.2 Середньої складності

| Клас | Опис |
|---|---|
| `drift` | повільне відхилення показань від дійсних |
| `clock_skew` | розходження міток часу пристрою з реальним часом |
| `beaconing` | періодичність публікації стає строго регулярною |
| `energy_anomaly` | споживання електроенергії у неробочий час |

### 7.3 Складні

| Клас | Опис |
|---|---|
| `zone_incoherence` | показання давачів однієї зони суперечать одне одному |
| `gateway_group_loss` | узгоджена деградація всіх пристроїв одного шлюзу |
| `exfil_pattern` | лічильник вихідного трафіку шлюзу зростає непропорційно обсягу телеметрії |
| `sensor_swap` | два однотипні давачі обмінюються показаннями |

Класи `beaconing`, `rogue_device` та `exfil_pattern` відповідають ознакам
компрометації пристрою і розглядаються у розділі 1.5 пояснювальної
записки у термінах моделі MITRE ATT&CK.

## 8. Система оцінювання

Оцінювання здійснюється за стобальною шкалою.

| Складник | Балів | Спосіб оцінювання |
|---|---|---|
| Виявлення інцидентів | 30 | автоматично, зіставленням з еталоном |
| Конвеєр і вимірювання продуктивності | 15 | за звітом, з вибірковою перевіркою |
| Вузол IoT, MQTT, захищеність каналу | 15 | демонстрація |
| Пояснювальна записка | 20 | за критеріями п. 8.2 |
| Дашборд | 10 | демонстрація |
| Захист | 10 | доповідь та відповіді на запитання |

Складник «Виявлення інцидентів» обчислюється як зважена повнота: складні
інциденти мають вагу 2,5, середні — 1,5, прості — 1,0.

### 8.1 Калібрування складника «Виявлення інцидентів»

Шкалу перевірено на еталонній реалізації, побудованій із застосуванням
робастної статистики (медіана, MAD), рухомих вікон, аналізу інтервалів
між повідомленнями та зіставлення пристроїв між собою — тобто методів,
передбачених програмою дисципліни. На дванадцяти варіантах така
реалізація показала повноту 96 %, точність 79 % і **25,5 з 30 балів**
(від 20,0 до 30,0).

| Балів | Тлумачення |
|---|---|
| менше 12,0 | детектори фактично не працюють |
| 12,0 – 19,9 | знайдено переважно прості інциденти |
| 20,0 – 25,9 | рівень, порівнянний з еталонною реалізацією |
| 26,0 і більше | високий результат |

> Наведені числа є верхньою межею, а не типовим результатом: еталонну
> реалізацію написано з повним знанням того, як саме інциденти
> вносяться у дані. Студент такого знання не має і спирається лише на
> навчальний набір, тому нижчий результат є очікуваним і не свідчить
> про помилку.

Якщо фактичні результати групи виявляться істотно нижчими за наведені
орієнтири, бали за складник може бути перераховано за фактичним
розподілом — лише в бік підвищення.

Жоден інцидент у жодному варіанті не є невиявним: придатність до
виявлення перевіряється автоматично для кожного згенерованого варіанта.

### 8.2 Критерії оцінювання пояснювальної записки

- відповідність змісту поставленим завданням;
- обґрунтованість обраних методів і повнота їх порівняння;
- якість інтерпретації отриманих результатів;
- наявність власного аналізу, а не переказу джерел;
- дотримання вимог до оформлення та наукового стилю.

### 8.3 Захист

Доповідь — до 7 хвилин, із демонстрацією працездатного дашборда.

Під час захисту студенту **надається раніше не відомий набір даних**, на
якому він запускає власний конвеєр і отримує результат у присутності
комісії. Нездатність виконати цю дію є підставою для оцінки
«незадовільно» (п. 8.4).

### 8.4 Підстави для оцінки «незадовільно»

- зміст роботи не відповідає завданням;
- картка результатів не відповідає виданому варіанту;
- конвеєр непрацездатний на незнайомих даних;
- відсутні посилання на використані джерела;
- обсяг записки менший за 20 сторінок.

## 9. Академічна доброчесність

Набір даних кожного студента є унікальним, тому унікальним є і правильний
результат. Подання чужих результатів виявляється автоматично: зіставлення
з еталоном дає нульову оцінку за складник, а картка результатів містить
величини, які не відповідають виданому варіанту.

**Щодо використання систем штучного інтелекту.** Використання таких систем
для написання коду, пошуку помилок і опрацювання літератури
**дозволяється** за умови зазначення цього у звіті. Відповідальність за
коректність запуску конвеєра, інтерпретацію результатів і захист
отриманих значень у будь-якому разі залишається за студентом.

Не допускається: передавання власного набору даних або результатів іншим
студентам, подання результатів, отриманих не власним конвеєром,
а також внесення у звіт показників, не відтворюваних на власних даних.

## Додаток А. Схема повідомлення MQTT

Топік: `kursova/<variant>/<device_id>/<metric>`

```json
{
  "device_id": "esp32-047",
  "metric": "temperature",
  "value": 22.47,
  "ts": 1757000000,
  "seq": 1041
}
```

Повідомлення Last Will публікується у топік
`kursova/<variant>/<device_id>/status` із вмістом `{"online": false}`.

## Додаток Б. Обчислення полів картки результатів

```sql
-- кількість записів
SELECT count(*) FROM telemetry;

-- пристроїв у даних
SELECT count(DISTINCT device_id) FROM telemetry;

-- записів за показниками
SELECT metric, count(*) FROM telemetry GROUP BY metric ORDER BY metric;
```

Хеш переліку пристроїв обчислюється від відсортованого за зростанням
переліку `device_id` **з маніфесту**, об'єднаного символами переводу рядка
(`\n`), без завершального переводу рядка, у кодуванні UTF-8.
